# Scene 1 – Billing High-Volume Access Review: Expected Outcomes

## Scenario Purpose

Demonstrate TrustPulse detecting and triaging a billing staff member who accessed an
unusually high volume of patient records in a compressed time window — a pattern
consistent with inappropriate bulk access or data exfiltration reconnaissance.

The session is fully synthetic and uses real OpenEMR activity-log seeding so the
case is generated by the same production ingestion and rule engine used in live
deployments.

### Triggered rules

| Rule | Condition | Points |
|------|-----------|--------|
| R-02 Bulk Patient Access | ≥ 10 unique patients in one day (28 ≥ 10) | 25 |
| R-08 Volume Spike | ≥ 20 total accesses in one day (55 ≥ 20) | 20 |
| **Total** | | **45** |

Risk score 45 → `P2_MEDIUM` (threshold: 40–69).

## Evidence Package

The exported HTML evidence package (`trustpulse_evidence_{case_id[:8]}.html`) must:

- Show all 55 event rows in the event table
- Display patient identifiers as `PT-{16hex}` tokens — **never raw numeric PIDs**
- List both triggered rules (R-02 and R-08) with their point values
- Include the ingestion manifest hash and source batch SHA-256
- Include a `BILLING_ACCESS_REVIEW` assessment template with three checklist items:
  - Billing, payment, claims, or insurance reason
  - Assigned billing work queue or follow-up list
  - Supervisor confirmation if unclear
- Show the history maturity label and baseline basis note

## Reviewer Actions (Demo Flow)

1. Open TrustPulse dashboard → case appears in Open queue with `P2_MEDIUM` badge
2. Click the case → drawer shows 55 events, 28 unique patient tokens, 10:00–10:45 window
3. View Quick Review Guide → billing-specific checklist displayed
4. Click "Request Context" → send context request to `billing_ross@clinic.example`
5. Respond to context request (simulate response: "Processing EOB backlog queue")
6. Set case status to Resolved with disposition note
7. Export evidence package → HTML download with complete audit trail

## What Must NOT Happen

- No `PATIENT_ACCESS_REVIEW` case for dr_patel or frontdesk_kim
- No medium/high `AUTH_REVIEW` or `FAILED_LOGIN_REVIEW` case for frontdesk_kim
  (only 2 failed logins, below the threshold of 3)
- No raw numeric patient IDs (e.g., `42`, `17`) visible anywhere in the TrustPulse
  API responses or evidence HTML
- No second `PATIENT_ACCESS_REVIEW` case for billing_ross if the same seed data is
  re-ingested (idempotency via `source_log_id` uniqueness constraint)
